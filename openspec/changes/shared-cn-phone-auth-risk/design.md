## Context

手机号登录只服务中国大陆 `+86` 移动号码。短信是付费且可被脚本直接消耗的外部调用，因此安全边界必须位于供应商之前；客户端倒计时和供应商默认限频只能作为附加层。服务端还需要在控制依赖异常时允许用户验证已经收到的 OTP。

## Goals / Non-Goals

**Goals:**

- 提供国内手机号 OTP 登录和自动建号。
- 把每次付费调用置于强制 CAPTCHA、多维原子配额和硬预算之后。
- 支持紧急停发、审计、成本观测和攻击演练。

**Non-Goals:**

- 不发送国际、港澳台短信。
- 不把短信作为高价值操作的唯一长期认证保证。
- 不允许客户端直接持有供应商密钥或调用短信 API。

## Decisions

### 1. 服务端规范化后只接受 +86 移动号码

客户端输入只用于交互；服务端使用受维护的号码元数据规范化并验证国家/地区与号码类型。非支持号码在 CAPTCHA 和供应商调用前终止，避免形成国际费用旁路。

### 2. 每次发送都必须先完成 CAPTCHA

首期不做“低风险免验证”。CAPTCHA token 与动作、短有效期和单次使用绑定并在服务端校验。相比只在异常时弹出，这更严格且易于验证，代价是发送体验增加一步。

### 3. Redis 承担原子限额与预算预占

使用原子脚本或事务一次检查并占用手机号、安装实例、IP、网段、全局窗口和当日数量/费用预算。数据库保留 challenge、安全事件和可审计结果；Redis 不作为账号事实源。若 Redis 或 CAPTCHA 不可用，发送失败关闭。

### 4. 预算预占处理未知供应商结果

调用前创建 idempotency-bound 预占。供应商明确拒绝且确认不计费时释放；超时或结果未知保持占用并通过回执/对账收敛，禁止立即重发。相比调用后计数，这能硬性限制最坏支出。

### 5. OTP challenge 与明文分离

生成 6 位安全随机 OTP，短时通过 HMAC/带服务端 pepper 的验证摘要保存；日志、数据库和队列不保存明文。每个号码只保留受控数量的活动 challenge，新发送使旧码失效；验证错误达到上限即锁定。

### 6. 发送与验证采用不同可用性边界

新的发送必须依赖全部风控；验证已有 challenge 只依赖持久化 challenge 和验证限额，因此短信熔断或 CAPTCHA 故障不会让已收到验证码的用户无法完成登录。

### 7. 供应商适配器和运营双层控制

业务只调用 SmsSender 端口，腾讯云实现放在基础设施层。应用硬预算之外，同时配置腾讯云号码限频、发送阈值、告警联系人和账号级停用；远端 feature flag 可在应用发布之外关闭发送。

## Risks / Trade-offs

- [严格 CAPTCHA 降低转化率] → 首期优先控制费用和攻击面，基于真实指标另开 change 调整而非预留绕过。
- [共享 NAT 触发 IP 限额] → IP 只作为组合维度，使用分层窗口和清晰可重试提示，不以单一 IP 永久封禁。
- [攻击者使用代理和大量设备标识] → 组合网段、全局预算和供应商账户硬阈值，设备标识不作为唯一信任来源。
- [供应商成功但客户端超时导致重复请求] → 请求幂等键、活动 challenge 复用和未知预算不释放。
- [手机号回收或 SIM 换卡] → 后续为敏感操作增加近期认证与其他绑定身份，不把手机号作为业务主键。

## Migration Plan

1. 完成共享账号会话与国内短信/CAPTCHA 资质申请。
2. 建立 OTP、风险事件和幂等持久化，部署 Redis 原子预检但保持发送开关关闭。
3. 实现供应商沙盒/测试适配器和不发真实短信的全套自动化测试。
4. 接入真实供应商，先对白名单号码验证回执、费用、熔断和失败关闭。
5. 小流量开放并演练轮换号码、代理、Redis 故障、供应商超时和预算耗尽。
6. 通过监控验收后开放生产；异常时关闭发送开关，不回滚账号或已有会话。
