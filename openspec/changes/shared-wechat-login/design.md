## Context

该 change 在共享账号会话和 Apple 登录之后实施。微信移动应用授权由客户端唤起，但 AppSecret 和授权码换证只能在服务端；UnionID 的可用性取决于开放平台关联，OpenID 则具有应用范围。产品当前不含公开发布或即时通讯，因此不额外强制手机号。

## Goals / Non-Goals

**Goals:**

- 完成微信官方授权、服务端换证和共享账号登录。
- 首次微信登录自动建号且不收集手机号。
- 支持已登录账号主动绑定以及身份占用冲突。

**Non-Goals:**

- 不把微信昵称或头像作为可信身份或必填资料。
- 不自动合并两个已有账号。
- 不接入微信支付、分享或通讯录能力。

## Decisions

### 1. 客户端只传一次性 code 和授权关联状态

客户端通过官方 SDK 获取 code，使用高熵 state 关联本次请求；服务端持有 AppSecret 与微信端点换证并验证应用身份。禁止客户端提交 access token 作为唯一可信凭证。

### 2. 身份键同时表达 UnionID 与应用 OpenID 范围

可用时以开放平台范围的 UnionID 作为主要 provider subject，同时保存当前 AppID 范围 OpenID 用于审计和回调关联；没有 UnionID 时只在当前 AppID 范围使用 OpenID。环境和 AppID 进入 issuer scope，避免测试/生产串号。

### 3. 微信资料默认最小化

登录只请求完成身份认证所需的最小授权范围。昵称、头像等若非当前产品必要则不持久化；手机号不属于登录补充步骤。相比为了“资料完整”扩大收集，这更符合最小必要原则。

### 4. 自动建号和主动绑定复用共享事务

未登录流程把验证后的微信断言交给共享 find-or-create；已登录绑定要求当前会话近期有效并完成新的微信授权。身份占用时只返回冲突，不暴露另一账号信息。

### 5. SDK 不可用时保留其他入口

未安装微信、用户取消、SDK 配置错误和服务端换证失败映射为不同内部原因，但 UI 只展示安全且可行动的提示，并保留 Apple、手机号和未登录使用入口。

## Risks / Trade-offs

- [UnionID 缺失导致未来跨应用无法统一] → 明确保留 AppID scope，不进行猜测性合并；未来获得 UnionID 时需经验证迁移。
- [微信开放平台审核或 SDK 版本延迟] → 登录入口由远端开关控制，凭证和资质验收完成前不展示。
- [要求 Apple 先完成延后微信发布] → 这是明确的发布依赖，用于降低 iOS 审核与账号模型返工风险。
- [用户分别创建 Apple 与微信账号] → 提供登录后主动绑定；两个既有账号仍需未来独立合并流程。

## Migration Plan

1. 确认 Apple 登录已可用并完成微信开放平台移动应用资质。
2. 接入 iOS/Android 官方 SDK 配置和服务端换证适配器，保持入口关闭。
3. 增加 state、错误换证、UnionID/OpenID 范围和重复登录测试。
4. 接入共享自动建号、会话签发和主动绑定冲突测试。
5. 小范围真机验证未安装、取消、网络失败和多平台同账号行为后开放。
6. 回滚时关闭微信入口并保留既有绑定，用户仍可使用其他已绑定身份登录。
