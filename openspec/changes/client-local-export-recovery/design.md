## Context

菜谱数据库、导入数据库和受控媒体分布在多个本地位置。Android 默认 Auto Backup 可能分别备份数据库和文件且有容量限制；iOS Documents/Application Support 也可能进入系统备份。直接依赖平台快照无法保证跨文件一致性，也不能替代用户可见的备份。

## Goals / Non-Goals

**Goals:**

- 生成自包含、版本化、可验证的设备资料库备份包。
- 在任何写入前发现损坏、不兼容和空间不足。
- 让覆盖恢复失败后仍能打开原资料库。
- 明确排除认证秘密和不一致的系统备份状态。

**Non-Goals:**

- 不实现增量、合并、云上传或后台自动备份。
- 不承诺恢复第三方平台禁止复制的远端内容。
- 不以原始 SQLite 文件作为长期交换协议。

## Decisions

### 1. 备份包使用清单驱动的逻辑格式

备份包含版本化 manifest、规范化业务记录、媒体文件和逐文件摘要。相比直接压缩 Drift 数据库，逻辑格式能跨 schema 迁移验证并避免携带内部缓存、WAL 或设备路径。

### 2. 从一致快照导出

导出协调器先在数据库事务中读取稳定业务快照，再复制清单引用的媒体到临时目录并校验；新增编辑不进入本次快照。完成后原子生成最终包，失败删除临时产物。

### 3. 首期只做覆盖恢复

恢复先解包到应用受控临时目录，验证 manifest、版本、摘要、引用完整性和空间，再构建临时数据库与媒体树。用户确认后通过可恢复切换替换当前数据。合并需要实体冲突语义，留给后续 change。

### 4. 系统备份不作为产品级恢复协议

认证安全存储、设备 token、pending 网络状态和临时目录全部排除。对于数据库与必要媒体，平台配置必须采用一致策略；若无法保证媒体容量与一致性，则整体排除应用数据自动恢复并依赖显式导出，而不是接受部分恢复。

### 5. 备份包由用户选择保存位置

应用通过系统分享/文件选择器把完成的包交给用户，不静默上传。包可能包含敏感个人菜谱和图片，因此导出确认说明内容范围；加密备份可后续独立设计，首期不声称未实现的端到端加密。

## Risks / Trade-offs

- [大媒体导致临时空间翻倍] → 导出和恢复前估算空间，流式复制与摘要，并在不足时不改变当前数据。
- [未加密备份被用户放入不安全位置] → 导出前明确提示内容敏感性；若首发风险不可接受，应在实施前把加密纳入独立需求评审。
- [多数据库快照时间点不同] → 导出期间协调暂停相关提交或使用全局导出锁，manifest 只引用已完成的稳定记录。
- [旧版本无法理解新备份] → 使用 schema 版本和向前迁移器；版本过新明确要求升级。

## Migration Plan

1. 更新备份 contract，冻结首版 manifest 和内容范围。
2. 实现逻辑导出模型、媒体清单和摘要验证。
3. 实现临时工作区覆盖恢复和故障注入测试。
4. 配置两平台备份排除/包含规则并验证认证秘密不被恢复。
5. 增加 Profile 导出、恢复和数据持久性提示。
6. 用包含缺图、损坏包、旧 schema、空间不足和中断提交的样本验收。
7. 回滚 UI 时保留格式读取能力；不得生成无法再恢复的备份包。
