## Context

现有端侧流水线已经具备受控媒体持久化、逐页 OCR、版面分析、保守结构化、媒体修订号和处理代次，但质量治理仍是单段式调用：当前有效图片直接交给平台 OCR，Android 结果没有传回行置信度，Dart 传入的旋转次数未被两端原生识别实现消费，`RecipeDraftQuality` 主要反映字段是否齐全。现有五个 OCR 回放 fixture 只保存平台输出且缺少逐字标准答案，适合验证布局与结构化，却不能重新运行引擎或计算识别准确率。

该 change 跨越 Import Domain、Data、Feature UI、Android/iOS 平台适配、媒体派生文件和测试资产；设计必须继续满足离线优先、原图与用户编辑不丢失、单页增量重处理、旧 generation 不回写及 V1 Android-only 验收边界。动机与行为契约见 `proposal.md` 和 `specs/ocr-recognition-quality/spec.md`。

## Goals / Non-Goals

**Goals:**

- 把 OCR 质量拆成可诊断、可度量、可回归的阶段，而不是继续向单一解析器累积特例。
- 用有界成本比较原图与必要的增强候选，选择更可靠结果并可解释其来源。
- 让方向、坐标、置信度和文字质量风险贯穿统一 OCR 文档与确认流程。
- 将繁简等价匹配限制在内部搜索键，默认用户文字和证据始终保持 OCR 字形。
- 复用现有媒体修订号、处理代次、分页状态和用户编辑保护，避免建立第二套任务状态机。

**Non-Goals:**

- 不训练、微调或下载自有 OCR 模型，不接入云端 OCR、多模态 AI 或服务端 API。
- 不为小红书、下厨房等具体平台建立模板级裁剪或正文规则。
- 不承诺从不可辨认图片恢复图片中不存在的像素信息，也不自动编造缺失菜谱内容。
- 不把繁体、地区用字或合法繁简混排定义为质量错误。
- 不让 iOS 真机质量门槛阻塞当前 Android V1，但两端使用相同领域模型和坐标契约。

## Decisions

### 1. 质量治理分为像素预检、候选 OCR 和文本后检三段

处理链调整为：

```text
受控原图 / 用户裁剪图
  → 像素预检（方向、尺寸、模糊、对比度）
  → 原图 OCR
  → 必要时生成至多一个增强候选并 OCR
  → 候选评分与选择
  → 文本后检（有效行、噪声、关键内容风险）
  → 版面分析与菜谱结构化
  → 质量提示、纠错建议和用户确认
```

无关界面占比和菜谱正文覆盖往往需要先看到 OCR 坐标与文字语义，因此不伪装成纯图片预检能力：像素预检只处理无需理解文字的信号；首次 OCR 后的文本后检再决定是否突出裁剪引导。相比“识别前必须裁剪”，这种两段诊断不会惩罚清晰截图，也能为裁剪说明具体原因。

### 2. 原图永远参与基线，增强按需且最多增加一个候选

每页始终先保留原图候选。只有文字尺寸、模糊、低对比度等诊断命中且预处理预计可恢复时，才生成一个版本化派生图；首版预处理 profile 采用方向物理归一、受限尺寸调整、灰度/对比度和轻度锐化的保守组合，不默认使用强二值化。候选比较综合有效文字覆盖、可用置信度、乱码/孤立字符风险、菜谱关键区覆盖和新增噪声，不以“识别字符越多”作为唯一目标。

最多两个 OCR 调用为延迟、内存和电量设置明确上界。相比对所有图片批量生成多种滤镜，这能降低包体和计算成本；相比只识别增强图，原图候选提供稳定回退。派生图位于应用受控媒体目录，记录 profile/version 与来源内容修订号；候选落库前继续校验 processing generation，未选候选和失效派生文件可按受控清理规则删除。

### 3. 图片质量报告使用离散问题码，不形成一个虚假的总分

每页保存可空的 `ImageQualityReport`，包含例如 `wrongOrientation`、`blurred`、`textTooSmall`、`lowContrast`、`lowRecipeCoverage`、`excessChrome` 等问题码、证据摘要、推荐动作和诊断版本。UI 将问题转换为中文可行动说明，不向用户展示难以解释的百分比。

像素阈值和候选评分属于版本化策略配置，不进入业务数据库的权威语义。旧任务没有报告时视为 `unknown`，可继续使用现有结果，不强制迁移或批量重识别。

### 4. 旋转在 OCR 边界前物理应用，并统一变换坐标

当前 `rotationQuarterTurns` 只影响 Flutter 预览。新流程在建立 OCR 输入候选时把用户旋转物理应用到像素，平台 OCR 读取已定向输入；返回的像素宽高和左上原点归一化坐标天然对应用户看到的方向。这样避免让每个平台分别解释旋转参数并在结果侧重复变换。

备选方案是在 Android `InputImage` 和 iOS Vision handler 中分别传方向元数据，但文件 EXIF、用户旋转和平台坐标原点叠加后更容易产生差异。物理归一派生图增加一次受控文件写入，但更易回放、预览和跨平台验证，失败时仍可回退原图与现有错误流程。

### 5. 扩展统一 OCR 文档，但所有平台元数据均显式可空

`OcrLineEntity` 增加可选方向和识别语言，保留现有可选置信度；`OcrPageEntity` 增加引擎标识、引擎版本、预处理 profile/version、来源内容修订号和页面级质量结论。Android Adapter 读取引擎实际提供的行置信度、角度和语言；iOS 继续映射 Vision 置信度，并只写入平台确实返回或配置可证明的元数据。

`null` 表示能力未提供，真实 `0` 表示平台返回低值，两者不得混用。旧 JSON 缺少新字段时使用 `null`/`unknown` 默认值。相比在 Adapter 内直接丢弃低置信行，保留原始行让 Domain 能结合坐标与菜谱语义保守判断，也继续支持证据回看。

### 6. OCR 文字质量建立独立模型，不复用 RecipeDraftQuality

新增页面和文档级 `OcrTextQuality`，采用 `usable / needsAttention / insufficient` 等离散结论及问题码，描述乱码、关键低置信行、疑似漏行、噪声残留和元数据受限。`RecipeDraftQuality` 继续只描述结构是否足以进入确认。确认页组合两者：结构完整但文字需注意时定位风险行；文字清晰但来源缺少食材时只提示结构不完整。

不使用单一综合百分比，因为不同平台置信度不可直接校准，且“字段齐全”和“字符正确”属于不同维度。内部基准保留精确指标，用户界面只展示离散风险和下一步动作。

### 7. 原文、内部匹配键、建议和用户校对是四个单向层级

文字数据流为：

```text
机器 OCR 原文（保留字形与证据）
  ├─→ 内部匹配键（繁简等价、空格和单位归一；不展示、不回写）
  ├─→ 纠错建议（原文、候选、原因、证据、状态）
  └─→ 用户校对正文（主动采用、转换或手动编辑后产生）
          → 结构化草稿与用户字段保护
```

内部匹配键只用于识别“食材／食材”“步驟／步骤”等等价语义和词典查询，不得参与证据摘录或默认字段展示。词典同时接受简繁和地区用字；疑似 `耗油 → 蚝油`、`IO克 → 10克` 等上下文纠错只生成候选。整段繁简转换复用同一用户编辑层，先预览再确认，并保存一次可撤销的校对修订；拒绝状态与用户编辑保护一起持久化，防止重新整理静默采纳。

相比自动把全部内容规范成简体，该设计不损害繁体用户；相比完全不做归一，它仍允许结构化器识别繁体分区和菜谱术语。

### 8. 质量基准分公开可提交集与本地私有集

仓库内新增带许可说明的图片级 benchmark：图片必须为自制、合成、脱敏或明确授权，并包含人工标准文字、有效/噪声区域、菜名、食材、步骤、字形类型和退化场景标签。现有仅含 OCR 输出的 replay fixture 继续负责布局与结构化确定性测试，不冒充引擎准确率测试。

本地私有集通过版本控制外目录运行相同 runner，其 manifest 使用相对路径且报告只输出样本匿名 ID、场景标签和聚合指标。指标至少包括字符错误率、有效行召回、无关内容残留、关键字段准确率/列表 F1、用户校对编辑距离、单页耗时和峰值内存。先记录当前基线，再为各场景设质量预算；后续变更必须通过预算，目标场景的改善不能以其他关键场景明显回退为代价。

### 9. Android 是发布质量门，iOS 是契约回归门

Android 使用打包的中文 ML Kit 模型完成无网络真机 benchmark、旋转、裁剪、增强回退和繁简保留验收。iOS 使用 Vision 回放与平台单元/集成验证确保方向、坐标、置信度和字形契约不退化；iOS 真机指标在 V1 稳定后补齐，不阻塞 Android V1。

这延续现有产品发布决策，避免专项重新扩大双平台发布范围，同时防止 Domain 模型被写成 Android 专用。

## Risks / Trade-offs

- [双候选 OCR 增加延迟、电量和峰值内存] → 仅在诊断命中时生成一个增强候选，串行处理页面并在 benchmark 中设置性能预算。
- [预处理可能放大压缩噪声或损伤浅色字] → 原图候选永远存在，候选选择检查有效正文保留并在不确定时偏向原图。
- [平台置信度跨引擎不可直接比较] → 只在同平台策略内校准阈值，跨平台使用离散问题码和各自质量预算。
- [裁剪引导过于频繁会增加用户成本] → 清晰图片零打断；无关内容判断在首次 OCR 后结合正文覆盖，只突出最相关的一个行动。
- [词典纠错会把合法繁体或地区用字误判为错误] → 默认不改写，只生成带原因的建议；繁简等价仅存在于内部匹配键。
- [图片级 benchmark 增加仓库体积和版权风险] → 控制样本尺寸与数量、记录许可来源，真实用户素材只进入 gitignored 私有集。
- [旧任务缺少新质量字段] → 使用向前兼容默认值，不强制重识别；用户主动重试时才产生新版本元数据。

## Migration Plan

1. 先更新产品、MVP、导入服务、媒体服务和决策日志，建立准确率指标与不默认转换繁简的权威边界。
2. 扩展 OCR/媒体持久化模型并提供旧 JSON 默认值测试；旧任务保持可读，已有用户校对与确认字段不迁移、不覆盖。
3. 建立图片级 benchmark runner，记录当前 Android 基线与质量预算，再开始优化，防止无法归因的规则堆叠。
4. 修复物理旋转和平台质量元数据，验证坐标证据，再接入像素预检、单增强候选和选择策略。
5. 接入文字质量模型、条件式裁剪引导、内部繁简等价匹配和建议式纠错，最后完成 Android 无网络真机回归。
6. 若新策略产生严重回退，可关闭增强候选和建议生成，继续使用原图 OCR 与现有恢复流程；原图、机器 OCR、用户校对及正式菜谱均不因回滚丢失。未被引用的预处理派生文件交由现有受控媒体清理机制回收。

## Open Questions

- 各退化场景的具体质量预算数值将在首轮图片级基线产生后写入 benchmark 配置；这只校准验收阈值，不改变上述行为、数据层级或任务拆分。
