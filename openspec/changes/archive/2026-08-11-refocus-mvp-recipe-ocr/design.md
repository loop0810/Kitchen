## Context

现有应用已经将 Recipe、Import、Data 和根 App 协调拆成独立边界。图片导入会先持久化受控文件和 ImportTask，平台 OCR 返回带页码与坐标的文档，本地结构化生成带来源、可信等级和证据的 `RecipeDraftEntity`；但 Repository 还没有媒体编辑和分页失败命令，确认 UI 也会在根 App 映射到普通 Recipe Editor 时丢失字段证据。

Recipe 数据库已经存在 `lastCookedAt`、`cookCount` 和相应查询语义，详情页存在尚未接通的“开始烹饪”按钮，但项目没有 CookSession、计时器、通知或烹饪 Feature。参见 `proposal.md` 和两个 capability 规格。

## Goals / Non-Goals

**Goals:**

- 在不破坏现有本地菜谱数据的前提下彻底移除面向用户的烹饪运行时承诺。
- 让 Import Domain 成为图片顺序、处理版本、分页结果、草稿来源和确认状态的权威源。
- 让媒体修改、OCR 和草稿合并具备可恢复、增量和防止过期异步结果回写的语义。
- 保持 Feature 之间不直接依赖，由根 App 只承担最终 Import Draft 到 Recipe 写入的协调。
- 让账号个性化食谱配置通过服务端同步和本地缓存形成单一读取源，并由根 App 向 Profile、Import 和 Recipe Editor 注入。

**Non-Goals:**

- 不删除准备时间、烹饪时间、火力、温度等菜谱描述字段。
- 不引入云端 AI、模型下载、完整菜谱同步或付费权益；账号能力本轮只接入个性化食谱配置所需的最小会话与服务端网关边界。
- 不在本次重做 OCR 引擎或为具体内容平台编写版式规则。
- 不补齐本次范围以外的完整菜谱编辑、iOS Share Extension 或发布准备工作。

## Decisions

### 1. 产品范围按“永久移除”处理

权威文档将删除逐步烹饪和烹饪记录章节、CookSession 核心实体、烹饪服务导航与验收项，并新增决策记录替代所有把烹饪列为核心闭环的旧决策。代码移除详情 CTA、烹饪历史筛选和排序，但继续把“查看完整步骤”作为核心详情能力。

选择永久移除而不是标为“非 MVP”，是为了防止后续设计和架构继续为一个没有产品方案的能力预留 package、平台权限和数据流。

### 2. 兼容保留 SQLite 遗留列，移除公开语义

现有菜谱库中的 `lastCookedAt` 和 `cookCount` 暂不通过表重建删除。Domain Query、Entity、Repository 公共 API、筛选排序 UI 和测试不再依赖它们；历史持久化排序值在读取时迁移为“最近更新”，历史“做过”筛选回退为“全部”。新代码不再写入烹饪统计。

相比立即重建 SQLite 表，该方案避免为了隐藏两个无害列承担数据迁移风险。后续若因其他 schema 变更需要重建 Recipes 表，可顺带清理遗留列。

### 3. Import Media 使用稳定 ID 加内容修订号

每张媒体保留稳定 `mediaId`、处理顺序、忽略状态、受控原图引用、当前有效图引用和 `contentRevision`。旋转、裁剪或替换成功提交时递增内容修订号，并清除该页旧 OCR 状态；单纯重排只改变顺序和汇总结果，不重新识别页面；忽略不删除文件或旧结果，恢复后可按内容修订号复用。

裁剪和替换先写入临时受控文件，验证成功后以一次 Repository 操作切换引用，再清理旧派生文件。原始相册路径和外部分享 URI 不参与后续处理，也不得被删除。

### 4. 分页 OCR 状态代替单一完成布尔值

媒体页显式记录 `pending / processing / succeeded / failed`、稳定错误码、错误说明、对应内容修订号和可选 OCR Page。任务级失败只用于无法继续的情况；部分页面失败时任务进入可操作的等待确认/降级状态，而不是丢弃成功页。

现有只有 `ocrCompleted` 的数据在映射时兼容：有同版本 `ocrPage` 视为成功，否则视为待处理。避免仅靠一个布尔值无法表达重试中和失败原因。

### 5. 任务处理使用 generation 防止过期回写

ImportTask 增加单调递增的 `processingGeneration`。任何影响 OCR 汇总或自动草稿的媒体修改都会递增 generation。流水线开始时获取不可变任务快照，并在保存页结果、OCR 汇总、草稿或失败状态前以 Repository 原子操作验证 generation；旧 generation 的异步结果被安静丢弃。

这比仅依赖“任务是否取消”更可靠，因为用户可能在 OCR 运行时旋转、替换或重排图片，而任务本身仍然存在。

### 6. 增量重处理分为页面识别、正文汇总和草稿结构化

流水线按以下阶段执行：

```text
持久化媒体变更
→ 只识别 pending/failed 且用户要求重试的有效页面
→ 按当前顺序汇总 succeeded 页面
→ 合并用户校对正文与补充说明
→ 生成新的自动候选草稿
→ 按字段保护策略合并确认草稿
```

重排只从汇总阶段继续；旋转、裁剪、替换从目标页面 OCR 继续；仅编辑 OCR 正文或补充说明从结构化阶段继续。Repository 提供领域命令表达这些变更，Widget 不直接改 JSON 或数据库。

### 7. 用户校对正文与机器 OCR 分层保存

任务分别保存机器汇总 OCR、用户校对正文和用户补充说明，不再让 `saveOcrText` 同时承担机器结果与用户权威输入。原始逐页 OCR 永远可回看；重新识别更新机器层，但不会覆盖用户层。用户可以显式选择“使用最新识别结果重新开始校对”，该操作需要确认。

### 8. Import Feature 拥有可解释确认会话

`kitchen_import` 提供完整确认页面并消费 Import Domain 的版本化 Review Draft，不依赖 Recipe Feature。确认草稿保存字段值、来源、可信等级、证据、确认状态和顺序。根 App 在用户执行最终保存时，将已确认的公开 Import Draft 映射为 Recipe Domain 输入并调用现有 Recipe UseCase，再以 `importTaskId` 完成幂等关联。

相比直接把草稿映射进普通 Recipe Editor，这能在确认期间保留证据和风险语义；相比让 Import Feature 依赖 Recipe Editor，则继续遵守 Feature 不直接依赖的边界。可复用的纯视觉表单元素可以放在 Design System，业务模型不下沉。

### 9. 自动候选与用户字段使用保守合并

字段来源为 `userEdited` 或 `userConfirmed` 时保持用户值；来源为 `source` 或 `inferred` 时可由相同 generation 的新候选更新。若新候选与受保护字段冲突，将候选记录为提示，不自动覆盖。

MVP 对食材和步骤列表采用字段级保护：用户一旦编辑或排序整个列表，该列表作为整体受保护。虽然粒度较粗，但比在 OCR 重新分段后错误匹配列表项更安全；未来有稳定行级身份模型后再细化。

### 10. 文档与代码分两个可验证提交阶段

先更新权威需求和决策记录，使新范围成为事实源；再修改 Recipe 和 Import 实现。烹饪运行时服务文档从服务导航移除并删除，历史决策保留并由新决策明确替代。README 只在工程入口或可运行功能发生变化时同步更新。

### 11. 个性化食谱配置采用远端同步、本地缓存单一读取源

Recipe Domain 定义配置实体与 Repository 契约；Recipe Data 负责 Drift 缓存、待同步状态和可注入的远端网关。应用启动先读取缓存供 UI 使用，再执行同步：存在待上传修改时优先推送，其他情况拉取服务端；首次账号配置由服务端响应默认值。同步失败保留缓存和 pending 状态，不阻塞本地核心流程。

Profile Feature 只通过注入的 UseCase/Repository 管理配置；Import Feature 接收根 App 映射后的选项列表；Recipe Editor 订阅相同 Repository 缓存流。确认导入页不再提供管理入口，避免入口重复和 Feature 间直接导航。

### 12. 时间选择器保存总分钟但按小时分钟编辑

Domain 与数据库继续保存总分钟，避免 schema 变化。Presentation 将总分钟拆为小时与分钟两列；分钟使用循环滚轮，选择 2 小时时强制分钟归零，关闭选择器时再合并为不超过 120 的总分钟。该转换只属于 UI，不改变菜谱领域模型。

## Risks / Trade-offs

- [媒体 JSON 中加入更多状态可能增加迁移和并发复杂度] → 所有媒体变更通过 Repository 原子命令并增加旧 JSON 默认值测试。
- [异步平台 OCR 无法真正取消] → 使用 generation 阻止过期结果落库，允许原生调用自然结束而不污染当前任务。
- [保留原图与裁剪派生图增加存储占用] → 删除或替换任务时统一清理受控引用，启动时继续执行孤立文件清理。
- [字段级列表保护会错过部分新识别内容] → 将新候选作为冲突提示展示，由用户主动采纳；安全优先于自动填充率。
- [SQLite 遗留烹饪列仍存在] → 从公共 Domain 和 UI 隔离并记录为兼容债务，不让它们影响任何用户行为。
- [独立 Import 确认表单可能与 Recipe Editor 产生视觉重复] → 共享 Design System 视觉组件和字段文案规范，不共享业务状态或让 Feature 直接依赖。
- [服务端或账号会话尚未配置] → 远端网关保持可注入，缓存内置默认值并记录 pending；缺少会话时不伪造同步成功，待账号服务接入后复用同一契约。

## Migration Plan

1. 先更新产品、MVP、菜谱、导入服务、服务导航和决策日志，删除烹饪服务文档及所有当前/未来承诺。
2. 移除 Recipe 层烹饪历史筛选排序、详情 CTA 和公开统计字段；为旧排序偏好增加兼容映射并运行数据库回归测试。
3. 扩展 Import Domain/Data 的媒体修订、分页状态、generation、校对正文、补充说明和确认草稿持久化，提供旧任务默认迁移。
4. 实现图片管理与失败降级 UI，再实现可解释草稿确认 UI 和根 App 最终保存协调。
5. 完成单元、Widget、数据库迁移和真实 OCR 回放，以 Android 无网络真机验收作为当前 V1 完成条件；iOS Vision 适配器与回放覆盖继续保留，真机验收延期到 V1 稳定后且不阻塞本 change。

回滚时可恢复旧 UI 与 Query 枚举；兼容保留的 SQLite 列使范围回滚不需要逆向数据迁移。Import schema 升级必须提供向前迁移，回滚旧版本前需避免让旧客户端读取它不理解的新任务 JSON，开发阶段通过清理测试数据处理。
