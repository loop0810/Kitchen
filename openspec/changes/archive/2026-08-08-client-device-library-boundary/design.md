## Context

当前菜谱数据库是设备本地权威源，尚无云备份；个性化配置却使用固定单例行保存服务端 revision 与 pending。引入账号后，单例缓存可能把账号 A 的数据上传到账号 B，而若给全部菜谱立即增加账号 owner，又会错误暗示登录已完成云端归属。

## Goals / Non-Goals

**Goals:**

- 让现有菜谱在账号状态变化时保持原样和离线可用。
- 隔离真正属于账号的缓存与 pending。
- 向用户准确表达登录、备份和卸载的区别。

**Non-Goals:**

- 不提供 App 内多用户私密资料库。
- 不把本地菜谱关联或上传到账号。
- 不实现本地资料库合并或云端恢复。

## Decisions

### 1. 菜谱使用 device library 语义而非 user owner

现有 Recipe、Collection、ImportTask 和媒体继续属于当前安装可访问的设备资料库，不新增 `ownerUserId`。这保持当前离线模型，避免登录瞬间产生未实现的上传、切换和冲突语义。

### 2. 账号状态只影响账号服务数据

登录、退出和切换只改变 Session 与账号命名空间；Recipe 查询不按账号过滤。UI 明示共享设备上不提供 App 内隔离，隐私依赖操作系统设备保护。

### 3. 个性化缓存改为命名空间键

以稳定 `account:<userId>` 和 `device:anonymous` 命名空间替代固定 `id=1`。Repository 的每次读写和同步都捕获目标 namespace；异步请求返回时再次确认 namespace，避免切换账号后的过期回写。

### 4. pending 永远携带所属账号

pending 不能作为“当前账号的待办”隐式解释。同步任务按 owner namespace 选择凭证；非当前账号 pending 可保留但不自动用当前会话上传。

### 5. 删除账号默认保留本地资料库

账号删除确认页将服务端删除和“同时清除此设备全部本地资料”拆为两个操作。清除本机需要再次确认、关闭数据库连接并清理所有受控媒体；失败必须报告未完全清除。

## Risks / Trade-offs

- [切换账号仍看到同一菜谱可能超出用户预期] → 首次切换和设置页清楚说明设备资料库语义，不宣传多用户隔离。
- [旧单例 pending 无法确定所属账号] → 迁移到匿名命名空间且不自动上传，首次登录由用户后续编辑生成账号 pending。
- [异步同步在账号切换后覆盖缓存] → 请求绑定 namespace、响应提交前比较当前目标并写回原 namespace。

## Migration Plan

1. 更新产品、契约和决策日志，先明确设备资料库语义。
2. Drift 升级新增 namespace，并把旧单例配置迁移为匿名命名空间。
3. Repository 和根装配按会话选择账号命名空间，增加并发切换测试。
4. 增加登录后说明、退出/切换提示和账号删除的本机清除选项。
5. 回滚 UI 时保留新 schema；不得重新使用无 owner 的全局 pending 上传。
