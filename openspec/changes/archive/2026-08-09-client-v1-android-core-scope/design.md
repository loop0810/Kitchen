## Context

当前 Flutter 客户端已经具备菜谱、导入、OCR、编辑和本地数据库的多 package 边界，`refocus-mvp-recipe-ocr` 已覆盖大部分图片恢复与草稿确认设计，但仓库仍有登录、备份、iOS 分享和服务端相关并行 change。V1 需要以现有本地能力为基础收敛发布依赖，而不是引入新的平台或云端架构。

## Goals / Non-Goals

**Goals:**

- 形成 Android 单平台可验收的本地菜谱闭环。
- 让导入任务、OCR 失败和草稿确认具备中断恢复与手动降级能力。
- 用明确的 V1 门槛阻止登录、服务端和 iOS 能力反向阻塞发布。
- 保留未来恢复 iOS、账号和备份能力所需的边界，但不让它们成为当前核心流程依赖。

**Non-Goals:**

- 不重做 OCR 引擎或接入云端 AI。
- 不实现账号、同步、云端备份或支付。
- 不为了 V1 删除未来 change 的规划文件。
- 不在本 change 中实现业务代码；实施由后续 apply 阶段完成。

## Decisions

### 1. Android 作为 V1 唯一发布平台

使用 Android 分享、相册和端侧 OCR 完成第一版真实验收。iOS 相关代码和规划保留，但不作为构建、测试或发布门槛。相比同时维护双端，这能把验证集中到一条完整用户路径。

### 2. 本地资料库作为 V1 唯一权威数据源

菜谱、导入任务、OCR 结果和媒体文件继续由本地数据库及受控目录管理。账号配置和远端网关不进入核心依赖；相比为了未来同步提前引入会话和冲突模型，本方案更符合离线优先目标。

### 3. 以“可恢复导入”作为最大技术重点

先持久化原始输入，再处理 OCR；沿用处理 generation、逐页状态、用户校对层和草稿确认语义。识别失败时保留任务并转为手动路径，而不是把自动识别成功率作为发布门槛。

### 4. V1 只保留稳定免费模板

模板渲染继续与菜谱数据分离，但发布验收只要求一套稳定免费模板和基础极简展示。手账扩展、购买和模板编辑器不进入核心任务。

### 5. 通过发布清单而不是功能数量判断完成

V1 完成条件是 Android 真机在无网络、未登录条件下跑通导入、校对、保存、搜索、详情和编辑，并通过 Dart 格式检查、静态分析、自动化测试。未达到这些条件前，不继续扩展外围功能。

## Risks / Trade-offs

- [Android-only 会暂时缩小用户覆盖面] → 在产品和 README 中明确这是 V1 发布策略；稳定后单独进行 iOS 兼容验收。
- [延期登录和备份可能让用户担心数据安全] → V1 强调本地资料库边界，并在发布前提供清晰的删除和数据保留说明；不伪造云端备份承诺。
- [本地 OCR 对复杂图片的成功率有限] → 将手动编辑、失败页重试、忽略和待完善保存作为一等路径。
- [现有文档与 change 仍包含较大 MVP 范围] → 以本 change 的 V1 规格和验收清单为当前实施入口，后续同步权威产品文档。

## Migration Plan

1. 先同步 V1 范围到产品文档、客户端 README 和决策记录。
2. 将 `refocus-mvp-recipe-ocr` 的 OCR 恢复、确认和 Android 验收任务设为主线，外围任务延期。
3. 在 Android 真机完成离线核心流程和自动化回归。
4. V1 稳定后，分别创建或恢复 iOS、账号、备份和同步的实施 change，不把它们混入本次发布。
