## 2. 产品概述

厨房手记是一款本地优先的个人菜谱管理应用。它帮助用户把分散在小红书、
抖音、Bilibili、下厨房、网页、截图和个人笔记中的做饭内容，整理成统一、
可搜索、可编辑、可执行的结构化菜谱。

核心价值不是再次建立一个内容收藏夹，而是完成以下闭环：

```text
看到做饭内容
→ 快速收入应用
→ 结构化 OCR / 本地保守解析
→ 用户检查和修正
→ 保存到个人菜谱库
→ 搜索并再次找到
→ 查看完整食材、步骤与来源
→ 持续编辑和积累个人经验
```

## 3. 产品目标

### 3.1 用户目标

- 跨平台保存有价值的做饭内容。
- 将视频、图文和截图转化为快速可读的菜谱。
- 通过分类、标签和搜索再次找到已保存菜谱。
- 做饭时快速查看食材、用量和步骤。
- 长期积累属于自己的做饭经验和修改记录。

### 3.2 项目学习目标

- 练习完整的 Flutter 客户端开发。
- 练习 iOS、Android 原生能力与 Flutter 的桥接。
- 练习 SQLite、数据迁移和本地优先设计。
- 练习组件化架构、依赖治理和跨组件通信。
- 练习 Riverpod、GoRouter、Drift 等技术的合理边界。
- 深度使用 Codex CLI、VS Code Codex 扩展和项目级指令。
- 学习结构化 OCR、版面分析、本地解析和降级策略。

### 3.3 MVP 成功标准

- 用户能够创建或导入一道菜谱并保存。
- 用户能够通过名称、食材或标签重新找到菜谱。
- 用户能够查看完整食材与步骤。
- 用户能够从详情页查看完整食材、步骤和来源。
- 网络不可用时，用户仍可完成图片导入、校对、菜谱创建和查阅。

## 4. 目标用户

### 4.1 核心人群

- 以女性用户为主要早期人群。
- 经常在家做饭或正在学习做饭。
- 经常从多个内容平台寻找菜谱。
- 重视生活记录、审美表达和个人整理。
- 希望再次使用收藏内容，而不是只完成一次性收藏。

### 4.2 包容性原则

- 视觉和文案不能排斥男性或其他用户群体。
- 不使用过度性别化的功能命名或引导。
- 用户可以选择极简或手账风格。

## 5. 用户痛点

1. 未及时收藏的内容之后很难再次找到。
2. 平台收藏夹缺乏有效分类，内容容易长期闲置。
3. 视频对只需要食材和步骤的用户来说读取效率低。
4. 多个平台之间的收藏和搜索不互通。
5. 平台链接可能失效，用户无法长期保留自己的做饭资料。
6. 原菜谱往往不包含用户自己的火候、口味和厨具调整。

## 6. 产品原则

- **本地优先**：个人菜谱的核心导入、浏览、编辑和查阅不依赖网络。
- **用户确认**：OCR 和本地解析结果是草稿，不能未经确认成为权威内容。
- **用户数据优先**：用户修改不能被重新解析或云端更新覆盖。
- **始终可降级**：OCR 或本地解析失败后仍可手动完成任务。
- **来源透明**：保留原链接、原作者、原文字和用户修改关系。
- **实用优先**：手账风格不能损害厨房场景的可读性。
- **克制扩展**：MVP 只实现个人菜谱闭环，不扩展为内容社区。

## 7. MVP 范围

### 7.0 V1 发布画像

本 MVP 的第一阶段发布版本（V1）限定为 Android 单平台、本地优先的个人菜谱工具。
V1 不要求登录、账号服务、网络连接、云端备份或 iOS 能力；这些能力属于 V1 稳定后
的后续发布，不得成为 Android 核心流程的前置条件。

V1 必须优先完成以下闭环：

```text
Android 分享或相册选图/文字
→ 导入箱持久化
→ 端侧 OCR 或手动整理
→ 用户校对确认
→ 保存为菜谱或待完善菜谱
→ 本地搜索、查看和编辑
```

V1 暂不作为发布前置条件的能力包括：iOS 客户端和 Share Extension、Apple/微信/手机号
登录、账号配置同步、本地备份恢复、云端同步、菜谱集增强、复杂模板、付费 AI、社区和
烹饪运行时。V1 视觉验收只要求一套稳定的免费模板和可读的基础菜谱详情。

### 7.1 MVP 包含

- 首页本地搜索。
- 系统分享入口。
- 应用内链接、文字和图片导入。
- 多张截图导入和端侧 OCR。
- OCR 行坐标、页序和识别原文持久化。
- 通用版面分析与本地保守解析。
- 草稿来源证据、可信等级、结构校验和手动补充。
- 本地菜谱数据库。
- 菜谱库、收藏、分类、标签、筛选和搜索。
- 手动创建和编辑菜谱。
- 完整菜谱详情。
- 极简、手账两种免费视觉风格。
- 用户可主动导出带版本、清单和校验值的本地备份包，并在恢复前确认覆盖影响。
- 登录保持可选；认证服务不可用时，本地菜谱核心流程继续可用。登录不等同于本地菜谱备份或同步。Apple 登录不要求手机号；中国大陆手机号登录若启用，必须先通过 CAPTCHA、限额和预算预检，且取消或服务失败不影响本地功能。

### 7.2 MVP 不包含

- 家庭多人共享。
- 社区、关注、评论和公开发布。
- 一周菜单规划。
- 冰箱库存管理。
- 自动生成购物清单。
- 营养和热量分析。
- 自动登录第三方平台。
- 绕过平台验证或反爬机制。
- 下载、搬运和公开传播原视频。
- 任意长视频的完整自动理解。
- AI 专属手绘步骤图。
- 多设备实时同步。
- 公共云端菜谱搜索。
- 端侧或云端大模型解析。
- 付费 AI 辅助及其订阅、次数包或权益结算。
- 通过激励广告补充 AI 次数。
- 逐步烹饪、计时器、通知、进度恢复和屏幕常亮。
- 烹饪会话、烹饪完成记录和依赖烹饪历史的筛选排序。

## 8. 信息架构

底部导航固定为：

1. 首页
2. 菜谱库
3. 导入箱
4. 我的

所有主动创建行为统一使用“创建菜谱”入口。选择面板只包含：

- 手动创建。
- 粘贴文章或链接。
- 选择图片。

系统分享属于外部入口，收到的内容直接进入导入箱，不在面板中重复展示。

一级页面顶部栏：

- 首页不展示顶部栏；菜谱库、导入箱和我的页面使用可收缩顶部栏。
- 页面初始展示大标题和副标题，随页面向上滚动，顶部栏逐渐显示并收缩为固定高度；
  副标题离开屏幕后顶部栏完全显示，向下滚动回到副标题时顶部栏淡化。
- 菜谱库的搜索、筛选和分段控制区吸顶时位于顶部栏下方，不遮挡顶部栏标题。

## 9. 功能需求

### 9.1 首页

首页保持极简，只承担搜索和创建意图。

必须包含：

- 主文案“今天想吃点什么？”。
- 搜索框，占位文案“搜索菜名、食材或标签”。
- “创建菜谱”统一入口。
- 底部主导航。

首页不展示：

- 最近保存。
- 收藏列表。
- 菜谱推荐。
- 使用统计。
- AI 权益卡片。

第一版搜索范围仅为个人本地菜谱。搜索不调用 AI，也不消耗未来付费权益。

### 9.2 未来搜索扩展

未来需要支持两个概念：

- **我的菜谱**：用户拥有、可编辑、可离线使用的菜谱。
- **发现菜谱**：服务端提供的公共菜谱目录。

不得使用简单的“本地 / 云端”字段代替归属关系，因为用户自己的菜谱可能
同时存在于本地和云端。

未来搜索结果可以提供：

```text
[ 我的菜谱 ] [ 发现菜谱 ]
```

公共菜谱加入个人菜谱库时，应创建可编辑的个人副本并保留来源关系。

### 9.3 菜谱库

必须提供：

- 双列手账缩略图视图。
- 列表视图接口预留。
- 搜索。
- 全部、收藏、待完善快速筛选。
- 主分类筛选。
- 食材、烹饪方式、时间、难度、标签等筛选接口。
- 最近更新、最近保存和菜名等排序接口。
- 菜谱集。
- 长按多选和批量操作接口。
- 回收站与恢复接口。

默认排序为最近更新。

当前版本的菜谱库使用 `[菜谱] [菜谱集]` 分段入口：

- 除点击分段按钮外，支持左右滑动切换；往返后保留各自滚动位置以及菜谱页的
  搜索、筛选和排序状态。
- 菜谱和菜谱集共用顶部栏与分段切换组件；菜谱模式搜索菜名、食材或标签，菜谱集
  模式搜索菜谱集名称及其成员菜谱，筛选项隐藏并仅保留右侧“创建菜谱集”入口。
  菜谱集模式将搜索框缩短并与创建入口并排；分段选中块随点击动画和页面手势连续滑动。
- 菜谱集允许重名，名称去除首尾空格、不能为空且最多 40 字。
- 菜谱集按创建时间升序稳定展示，新集合追加到末尾，不提供集合自身的手动排序。
- 菜谱集使用响应式双列 3:4 书籍卡片；大文字或极窄宽度降级为单列。单击非空
  集合直接进入手账阅读器，单击空集合进入成员添加引导；长按在触点附近显示
  编辑、管理成员和删除。
- 创建和编辑可从系统相册选择图片，并固定为 3:4 手动裁切、压缩后保存在应用
  受控目录；可重新裁切、替换或恢复内置书封，不提供相机入口。
- 集合成员按用户顺序展示；新成员按选择顺序追加，成员可侧滑移除并撤销，也可
  长按拖动后原子保存完整顺序。软删除菜谱隐藏但保留原集合位置。
- 一道菜可属于多个菜谱集；删除集合不删除菜谱。本轮提供基础手账阅读器，仍不
  提供菜谱集简介。

菜谱排序支持最近更新、最近保存和菜名，并跨启动保存上次
选择。菜名排序为中文拼音优先、英文忽略大小写、数字和符号最后；搜索与快捷筛选
继续和当前排序组合。

回收站采用完整软删除流程：删除后保留 30 天，可恢复到删除前的
`ready/incomplete/archived` 状态并保留原集合关系，也可经二次确认永久删除。应用
#### 9.3.1 手账缩略图

展示：

- 菜谱所选手账模板的第一页缩略预览。
- 菜名。
- 部分主要食材及数量。
- 收藏状态。
- 待完善状态。

缩略图不承担完整内容阅读。它不展示全部食材、详细步骤和长来源文本，点击后
直接进入当前菜谱的完整详情与详细步骤页面。

#### 9.3.2 菜谱集

- 用户可以创建、编辑封面、重命名和删除菜谱集。
- 一道菜可以加入多个菜谱集。
- 删除菜谱集不会删除其中菜谱。
- 菜谱集成员支持追加、侧滑移除与撤销、长按拖动排序。

#### 9.3.3 分类与标签

- 每道菜只有一个主分类。
- 系统属性允许多选。
- 用户标签允许自由创建。
- 自动建议的分类和标签必须允许修改。

主分类初始值：

- 家常菜
- 主食
- 汤羹
- 烘焙
- 甜品
- 小吃
- 饮品
- 酱料与配菜
- 其他

#### 9.3.4 手账阅读器

手账阅读器仅用于查阅已经创建完成的手账菜谱，不承担编辑。
阅读器内不提供菜谱集编辑、成员管理或其他管理操作入口。

每页只展示一道菜谱，内容包括：

- 菜名。
- 部分主要食材及数量。
- 当前菜谱选择的手账模板与装饰。
- 进入完整菜谱详情和详细步骤页面的入口。

阅读器不直接展示完整食材和详细步骤。

手账阅读器只能通过选择一个已经创建并整理好的非空菜谱集打开：

- 单击菜谱库中的手账缩略图不会进入阅读器。
- 单击非空菜谱集书封直接进入阅读器；单击空集合进入成员添加引导。
- 阅读范围固定为当前菜谱集，阅读器不得通过继续滑动进入其他菜谱集或未加入
  当前菜谱集的菜谱。
- 空菜谱集不能进入阅读器，并引导用户先添加菜谱。

阅读顺序：

- 中文标题排在英文标题之前。
- 中文标题按完整拼音排序，并以拼音首字母形成 `A-Z` 分组。
- 英文标题忽略大小写按字母顺序排列。
- 数字、符号或无法生成排序键的标题排在中文和英文之后。
- 排序键相同时依次使用标准化标题和菜谱 ID，确保顺序稳定。

进入阅读器时，默认定位到当前菜谱集排序后的第一道菜谱。点击阅读器中的手账
或“查看详细步骤”后进入该菜谱详情；返回时恢复当前菜谱集和阅读位置。

### 9.4 导入

#### 9.4.1 输入类型

- 第三方应用分享的链接。
- 分享文案。
- 纯文字。
- 单张图片。
- 多张连续截图。
- 应用内粘贴。

MVP 不直接导入视频文件。

#### 9.4.2 接收规则

- 收到分享后先创建本地导入记录，避免内容丢失。
- 分享操作不强制打开主应用。
- OCR 和本地解析在主应用前台或平台允许的后台能力中执行。
- 无网络时仍能处理本地图片和文字。
- 失败记录不能自动消失。

#### 9.4.3 导入状态

```text
等待处理
正在提取
正在识别图片
正在整理菜谱
等待确认
处理失败
已保存
```

#### 9.4.4 解析顺序

1. 标准化输入和来源平台。
2. 提取公开可访问内容。
3. 使用端侧 OCR 识别图片文字，并保留页码、文本行和归一化坐标。
4. 按版面恢复阅读顺序，过滤跨页重复的边缘界面文字。
5. 使用通用菜谱语义保守解析食材、用量和步骤。
6. 记录字段证据和可信等级，校验结构完整性。
7. 交给用户确认；无法可靠分类的原文不强行写入字段。

不得将绕过第三方平台验证作为实现方案。

#### 9.4.5 删除导入任务

- 导入箱所有状态的任务都支持向左侧滑露出删除按钮，不以完全滑动直接删除。
- 删除处理中任务前明确说明会停止处理，并先取消再删除；流水线发现任务被删除后
  安全终止，不回写失败状态。
- 删除已保存任务只删除导入记录，不删除正式菜谱。
- 其他任务删除时同步清理原始内容、中间结果和应用受控图片；不得删除受控目录外
  的文件，清理失败留给后续孤立文件清理。

### 9.5 图片模糊降级

OCR 结果不足时必须允许：

- 重新选择图片。
- 调整图片顺序。
- 裁剪或旋转图片。
- 修改 OCR 结果。
- 输入自然语言补充说明。
- 手动增加食材。
- 手动增加步骤。
- 忽略某张图片继续。
- 保存为待完善菜谱。

用户手动补充的内容可信度高于本地推断结果。

图片任务需要展示缩略图、用户顺序、忽略状态和逐页 OCR 状态。用户调整顺序只
重新汇总和结构化；裁剪、旋转或替换单图只重新识别受影响页面，其他成功页面继续
复用。多图中的单页失败不得清除成功结果，必须允许只重试、替换或忽略失败页。
处理期间发生媒体变更时，旧处理结果不得回写当前任务。

### 9.6 本地整理与确认

OCR 与本地解析输出必须是“菜谱草稿”。

确认页面按以下区块展示：

1. 来源与问题摘要。
2. 基础信息。
3. 食材和用量。
4. 准备工作。
5. 烹饪步骤。
6. 分类和标签。
7. 来源信息。

需要区分：

- 原文明确提供。
- 本地推断。
- 用户手动填写。
- 用户已经确认。

低可信内容使用温和提示，不使用难以理解的百分比。

每个自动字段需要提供来源、离散可信等级和可用的图片页或 OCR 摘录证据。机器
OCR 汇总、用户校对正文和自然语言补充分别保存；重新识别不得覆盖用户校对内容。
用户编辑或确认字段具有最高优先级，重新整理产生冲突时保留用户值并展示候选。
确认进度自动持久化，退出后可以继续。

确认页的结构化选择遵循以下约束：

- 主分类、标签和难度统一读取账号个性化配置缓存；首次缓存为空时使用服务端默认
  文案，离线启动时使用客户端同版默认值回退。
- 主分类与难度使用单选下拉框，标签使用可多选下拉入口；默认难度依次为“入门、
  简单、中等、难”，无法可靠解析时使用配置首项。
- 基准份量使用 1～10 人选择器；准备时间和制作时间使用小时、分钟双列选择器，
  分钟列循环滚动，最高均为 2 小时。无法可靠解析时保持待选择，不强行补值。
- 分类、标签和难度的管理入口仅位于“我的 → 个性化食谱”；确认页不提供管理入口。
  修改先写应用缓存，再通过可注入账号服务网关同步；失败时保留待同步状态，不阻塞
  离线确认。

用户可以：

- 修改任意字段。
- 调整食材顺序。
- 调整步骤顺序。
- 保存不完整菜谱。
- 保存并查看详情。
- 暂存稍后处理。

### 9.7 未来付费 AI（非 MVP）

- AI 辅助不属于当前 MVP，也不得被本地导入流程自动调用。
- 未来仅在用户主动选择、确认付费权益并授权上传后执行。
- 具体采用订阅、次数包或组合方式另行确认。
- AI 结果仍是可编辑草稿，不能覆盖用户已经编辑或确认的内容。
- 无权益、无网络或用户拒绝上传时，本地 OCR、解析和手动编辑始终可用。
- API 密钥不得写入客户端。

### 9.8 激励广告（非 MVP）

当前没有通过广告发放 AI 次数的已确认需求。若未来引入，必须重新评审并更新
版本范围；广告不得影响本地创建、浏览、编辑或详情。

### 9.9 手动创建与编辑

必须支持：

- 菜名。
- 简介。
- 封面。
- 基准份量。
- 准备时间、烹饪时间。
- 难度。
- 主分类和标签。
- 食材名称、用量、单位、预处理、可选状态。
- 准备工作。
- 烹饪步骤。
- 长期笔记。
- 来源信息。
- 展示风格。

复杂编辑使用独立编辑模式，不在普通详情页进行大量行内编辑。

编辑草稿自动保存在本地；正式保存使用数据库事务。

当前最小创建流程要求：

- 菜名、主分类和可用模板为硬必填。
- 菜名为空或超过 120 个字符时在字段下方显示明确错误。
- 校验失败时一次性保存全部字段错误状态，无论字段是否在屏幕内。
- 全局轻提示显示第一条具体错误，避免使用含义模糊的通用提示。
- 食材或步骤为空时允许保存为待完善。
- 手账预览提示缩略图最多展示前 4 项食材，其他食材仍保留在详情中。
- 创建成功进入详情后保留返回按钮和系统返回手势。

### 9.10 完整菜谱详情

按照以下顺序展示：

1. 封面、菜名和简介。
2. 份量、时间、难度、分类。
3. 标签。
4. 食材和用量。
5. 准备工作。
6. 全部步骤。
7. 用户长期笔记。
8. 来源。
成品图不是必填项。无图时使用客户端主题模板生成封面。

### 9.11 食材与份量

食材需要同时保留：

- 原始用量文字。
- 可选的数值。
- 可选的单位。

“适量”“少许”“一小把”等内容不能强制数值化。

份量换算规则：

- 仅缩放明确数值。
- 不缩放“适量”等描述。
- 食材可以关闭自动换算。
- 不自动缩放火力、时间和锅具尺寸。
- 详情页临时换算不修改基准配方。

MVP 数据结构必须预留份量换算；完整 UI 可以在后续小版本实现。

## 10. 视觉需求

### 10.1 风格

MVP 免费提供：

- 极简风格。
- 手账风格。

未来付费提供：

- AI 手绘食材或步骤图。
- 手绘菜谱长图。
- 高级手账模板。
- 高清导出和打印排版。

### 10.2 手账风格

允许使用：

- 暖白纸张背景。
- 珊瑚红、黄油黄、鼠尾草绿、浅粉、雾蓝。
- 胶带、贴纸、色块和轻微错落。
- 少量纸张纹理。
- 手绘感分割线和标签。

限制：

- 长正文不能使用难读的手写字体。
- 不能采用完全自由、无法响应内容长度的排版。
- 装饰不能影响厨房场景的快速阅读。

### 10.3 主题切换

- 用户在“我的”设置默认风格。
- 菜谱默认继承全局风格。
- 用户可以为单个菜谱切换风格。
- 风格只改变表现层，不改变菜谱数据和交互流程。

## 11. 数据需求

### 11.1 核心实体

- Recipe
- Ingredient
- RecipeStep
- RecipeTag
- RecipeCollection
- ImportTask
- SourceSnapshot
- RecipeRevision
- UserPreference

### 11.2 数据来源层次

```text
原始来源材料
→ 本地结构化草稿
→ 用户当前菜谱
```

需要保存字段来源：

- source
- inferred
- userEdited
- userConfirmed

重新解析或未来 AI 更新时不得覆盖 `userEdited` 和 `userConfirmed` 内容。

### 11.3 生命周期

正式菜谱状态：

```text
待完善
内容完整
已归档
已删除
```

收藏属于独立属性，不属于生命周期状态。

删除进入回收站并默认保留 30 天。删除导入记录和删除正式菜谱互不隐式影响。

## 12. 架构与技术需求

### 12.1 组件化目标

采用 Flutter Pub Workspace 管理的多 package 组件化结构，内部 package 统一使用
`kitchen_*` 前缀：

- `kitchen_notes`：组合根、路由、依赖装配和跨 Feature 协调。
- `kitchen_app_core`：无领域含义的导航契约与横切能力。
- `kitchen_design_system`：主题、视觉常量和通用视觉组件。
- `kitchen_recipe_domain`：纯 Dart 实体、UseCase 和 Repository 接口。
- `kitchen_recipe_data`：Drift 数据库、Mapper 和 Repository 实现。
- `kitchen_home`。
- `kitchen_recipe_library`。
- `kitchen_recipe_editor`。
- `kitchen_import`。
- `kitchen_profile`。

依赖规则以项目根目录 `AGENTS.md` 为准。

### 12.2 跨组件通信

- Widget 局部交互使用 callback。
- 应用状态和依赖注入使用 Riverpod。
- 业务数据通过 domain use case 和 repository stream。
- 导航由 app 组件协调。
- Feature 之间禁止直接依赖。
- 不使用全局 EventBus。
- 异步跨组件流程使用明确的状态机或领域事件。

### 12.3 本地数据库

- 使用 Drift + SQLite。
- 数据库表结构必须支持迁移。
- 表结构变化必须增加 schema version。
- 关键查询和迁移必须有自动化测试。
- Presentation 层不得直接依赖 Drift 生成类型。

### 12.4 搜索接口

第一版实现本地搜索，但接口需要允许后续组合：

```text
LocalRecipeSearchSource
RemoteCatalogSearchSource
FederatedSearchCoordinator
```

搜索结果需要区分：

- 用户是否拥有。
- 是否已下载。
- 是否已同步。
- 是否来自公共目录。
- 是否可以加入个人菜谱库。

## 13. 隐私、版权与安全

- 图片或文字上传云端前首次明确告知用户。
- 用户可以查看和删除保存的原始材料。
- 云端服务只保存完成处理所需的数据。
- 不在客户端保存 AI 服务密钥。
- 保留第三方内容来源和原作者信息。
- 不提供绕过登录、反爬、版权保护或付费内容限制的能力。
- 个人整理内容默认不公开。
- 公共菜谱功能上线前需要单独设计授权、审核和版权处理。

## 14. 非功能要求

- 核心菜谱功能离线可用。
- 常规本地搜索结果应即时反馈。
- 导入任务允许失败、重试和恢复。
- 意外退出不能丢失导入内容或编辑草稿。
- 支持 iOS 与 Android。
- UI 应适配常见手机尺寸和系统文字缩放。
- 关键操作具备可访问性标签。
- 代码通过格式化、静态检查和自动化测试。

## 16. 推荐开发顺序

1. 以 Android 无网络、未登录的导入—确认—保存—搜索—查看—编辑闭环为主线。
2. 完成图片重排、裁剪旋转、替换、忽略和分页失败降级。
3. 完成带字段证据、可信等级和用户编辑保护的草稿确认。
4. 用真实 Android 截图持续完善结构化 OCR、通用版面分析和保守解析测试集。
5. 通过 Android 真机核心流程和自动化回归后进入 V1 发布准备。
6. V1 稳定后再恢复 iOS Share Extension、账号、备份同步、复杂视觉和付费 AI。
