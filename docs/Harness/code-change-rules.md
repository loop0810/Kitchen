# Kitchen Code Change Rules

全局 Harness 负责通用 Task 生命周期；本文件只定义 Kitchen 中代码、配置、生成文件、文档和平台工程的修改边界。

## 允许修改的范围

- Change 模式：当前 OpenSpec Task 明确列出的 `client/`、`server/`、`docs/`、`openspec/`、工具脚本或根配置。
- Direct 模式：开发者明确指定的低风险、局部、可逆文件；不得借 Direct 路径扩大到产品行为、共享契约、架构边界、跨文件工作流、数据/安全或外部服务。
- 为保持契约一致性而在当前 Change 明确列出的另一端适配或权威文档。
- 依赖变更只有在 Task 明确需要、写清用途和失败策略时才允许；服务端依赖必须同步 `pyproject.toml` 与 `uv.lock`。

## 不得直接维护的生成内容

- 不手工编辑 `*.g.dart`、构建目录、Flutter/Gradle/Xcode 派生目录或其他代码生成产物；修改生成源后按项目命令重新生成。
- 不提交密钥、签名材料、`.env` 生产值、设备私有数据、绝对路径或构建产物。
- 数据库迁移和锁文件属于可审查的生产输入，必须随对应源变更纳入 Scope，不与生成目录混淆。

## Scope 控制

- Change 模式只修改当前 Task 的 Scope；Direct 模式只修改开发者明确指定或完成局部任务必需的文件；两种模式都不顺手重构、格式化或清理无关文件。
- 发现必须扩大范围时先暂停，说明原因、影响和可选方案；不能通过临时兼容层、死代码、禁用校验或伪造状态掩盖缺口。
- 范围外但必须保留的既有修改写入 Report 的 `Deviations` 或 `Remaining Issues`，不能自动归入当前 Change。
- Feature 不得绕过既有依赖方向、路由契约或服务端模块边界；共享行为必须先落到对应 contract。

## 修改前

- Change 模式先读当前 Change、相关权威文档、接口和已知调用方；Direct 模式读取与局部修改直接相关的权威文档、接口和调用方。
- 先检查 Git 现场，确认哪些修改属于当前任务。
- Change 模式先切出可以独立验证的最小纵向切片；Direct 模式保持局部边界，发现需要扩展时转入 Change Gate 重新判断。
- 修改用户可见行为、共享契约、数据 schema、迁移、安全或外部服务时，按根 `AGENTS.md` 触发额外文档和验证。

## 修改中

- 保持客户端 Feature、Domain、Data、平台适配和根 App 的职责边界；不让 Feature 直接依赖其他 Feature、Drift 实现或平台 SDK。
- 保持服务端模块化单体边界；不因文档中的“服务”名称自动拆成微服务。
- 本地优先流程必须有离线、失败、取消、重试、恢复和幂等边界；网络能力必须有明确降级策略。
- 不为了让测试变绿而删除断言、放宽路径/身份校验、吞掉异常或把未实现行为标记成功。

## 修改后

- 检查差异、生成文件、调试输出、依赖锁定和文档链接。
- 记录实际修改文件、用户或系统可观察行为、失败策略、Reset 方法和验证证据。
- 任何偏离 proposal/design/spec、临时方案或未运行验证都写入 Report。
