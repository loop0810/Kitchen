# 备份与同步服务需求

## 1. 定位

备份与同步服务负责本地导出、恢复、未来云端备份和多设备同步。第一阶段只需
预留边界，不应让同步复杂度阻塞本地 MVP。

## 2. 阶段划分

### 阶段一：本地导出与恢复

- 导出结构化菜谱数据。
- 导出菜谱集和成员关系。
- 导出用户图片和必要模板引用。
- 生成带 schema version 的备份包。
- 导入前校验并展示影响。

### 阶段二：云端备份

- 用户主动备份。
- 加密上传。
- 显示上次备份状态。
- 新设备恢复。
- 不提供实时协同。

### 阶段三：多设备同步

- 增量同步。
- 冲突检测和解决。
- 删除墓碑。
- 模板权益和资源同步。
- 设备状态与重试。

## 3. 职责

- 定义可版本化导出协议。
- 从本地数据和媒体服务获取一致快照。
- 校验备份完整性和资源清单。
- 执行恢复或合并。
- 维护云端备份任务状态。
- 未来维护增量游标、版本和冲突。

## 4. 非职责

- 不取代本地数据库。
- 不让云端成为唯一可读来源。
- 不同步第三方平台受限原始内容，除非授权允许。
- 不自动公开用户菜谱。
- 不将备份和公共菜谱目录混成同一概念。

## 5. 备份内容

至少包括：

- Recipe 及完整详情。
- Tag 和 Collection。
- TemplateSelection。
- 长期笔记。
- 用户媒体资源。
- SourceSnapshot，可由用户选择。
- 用户偏好。

不包括：

- API Key。
- 临时缓存。
- 可重新下载的公共模板资源，除非离线恢复需要。
- 广告 SDK 本地状态。

## 6. 协议要求

备份清单包含：

- 产品和 schema 版本。
- 创建时间。
- 数据表或实体版本。
- 文件列表、大小和校验值。
- 加密信息。
- 可选内容说明。

恢复前验证版本、完整性和剩余空间。

## 7. 恢复策略

第一版可以选择：

- 覆盖当前本地数据。
- 合并到当前数据，后续。

覆盖前必须：

- 明确告知。
- 建议先导出当前数据。
- 使用事务或临时数据库验证。
- 失败后恢复原状态。

## 8. 同步冲突

未来原则：

- 用户已确认内容不能被较旧云端数据覆盖。
- 使用实体版本或更新时间不能单独解决所有冲突。
- 食材和步骤需要稳定子实体 ID。
- 删除使用墓碑并设置保留期。
- 无法自动合并时由用户选择版本。

个性化食谱配置不等待完整菜谱备份能力：客户端当前提供独立缓存、pending 重试和
可注入远端网关。应用启动时无 pending 则拉取账号配置，有 pending 则优先上传本地
修改；正式账号鉴权、配置接口和稳定选项 ID 仍由服务端实现补齐。

## 9. 隐私与安全

- 云端备份需要账号和明确授权。
- 传输使用加密连接。
- 服务端保存加密和访问控制策略。
- 用户可以删除云端备份。
- 日志不记录菜谱正文或图片内容。
- 账号删除流程包含备份删除规则。

## 10. 失败与恢复

- 网络中断：任务保持可重试。
- 上传部分完成：使用幂等分片或重新校验。
- 备份损坏：禁止覆盖当前数据。
- 版本过新：提示升级应用。
- 空间不足：恢复前检测。
- 权限或账号失效：本地数据继续可用。

## 11. 验收

本地导出阶段：

- 无网络可以生成备份包。
- 备份包包含版本和校验信息。
- 恢复失败不会破坏现有数据库。
- 用户媒体资源引用保持有效。
- 不导出密钥和临时缓存。

云端阶段上线前另行补充服务端容量、加密、删除和多设备冲突验收。
